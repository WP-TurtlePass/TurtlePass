> 제안서 초안
>
> 평가에는 [제안서 평가기준](evaluation.md#제안서-평가기준)을 적용한다. 기존 평가표는 참고용으로만 활용한다.
>
> 팀명은 제안 명칭이며, 팀원 이름과 개발 기간이 미정이므로 4인·8주를 가정했다. 구현 기준은 [요구사항](spec.md), 기술 계획은 [계획](plan.md), 진행 상태는 [현황](tasks.md)을 따른다. 아래 기능·성과는 개발 목표이며 구현·검증 완료를 뜻하지 않는다.

## 1. 프로젝트 개요

**siheung-tourpass**는 시흥시를 방문하는 가족 단위 방문객이 관심사에 맞는 관광 장소를 추천받고 체험·상점 혜택의 조건을 한곳에서 확인하고, 하나의 디지털 패스를 제시해 이용하며, 남은 혜택과 사용 결과를 확인한 뒤 피드백을 남기는 웹서비스다. 장소·지역·테마·동반 유형·혜택의 관계를 정의한 온톨로지로 추천 이유를 설명하고, 본인의 평가를 다음 추천에 반영한다. 가맹점 담당자는 같은 서비스에서 이용권의 유효성과 중복 사용 여부를 확인한다.

- **팀명(안): 이음** — 방문객의 체험과 지역 상점 방문을 잇는다는 뜻이다.
- **서비스명:** [요구사항의 명명 기준](spec.md#목적)을 따른다.
- **팀원:** [팀원 A], [팀원 B], [팀원 C], [팀원 D]. 역할은 7절에 제시한다.
- **핵심 가치:** 방문객에게는 이해하기 쉬운 이용 조건을, 담당자에게는 일관된 사용 확인 절차를 제공한다.

수업에서는 시흥시를 배경으로 한 **시연용 1일 패스 1종과 허구 가맹점 2곳**을 구현한다. 실제 제휴나 결제 없이도 ‘추천·탐색 → 발급 → 사용 확인 → 이력 조회·피드백 → 다음 추천’가 서버와 데이터베이스로 연결되는지 검증한다. 모든 상품·금액·발급 기록에는 ‘시연용·실제 사용 불가’를 표시한다.

## 2. 문제 정의와 필요성

### 목표 사용자와 불편

주요 사용자는 **주말에 자녀와 시흥시를 당일 방문하며 체험시설 이용 후 주변에서 추가 활동이나 휴식을 찾는 보호자**다. 실제 수요가 확정된 고객군이 아니라, 기존 거북섬 기획에서 시흥시로 범위를 넓혀 선정한 우선 검증 대상이다.

예를 들어 보호자는 체험과 음료 혜택을 살펴볼 때 무료 제공인지 할인인지, 추가 비용이 있는지, 예약이 필요한지, 언제까지 이용할 수 있는지를 알아야 한다. 이 조건이 여러 안내에 흩어져 있거나 서로 다른 표현으로 제공되면 방문 전에 비교하기 어렵다. 현장에서는 담당자가 패스의 유효기간과 이미 사용한 혜택을 확인할 수 있어야 한다.

추가로 방문객이 관심사·동반자에 맞는 장소를 고르기 어렵고, 이용 후 평가가 다음 선택으로 이어지지 않는다는 가설을 검증한다.

따라서 해결할 문제를 다음과 같이 설정한다.

> 방문객은 혜택의 실제 이용 조건과 남은 이용 가능 횟수를 쉽게 이해하기 어렵고, 담당자는 같은 조건에 따라 유효성·중복 사용을 확인할 수단이 필요하다.

이는 프로젝트의 **사용자 문제 가설**이다. 현재 방문객 인터뷰나 상점 업무 관찰을 수행한 결과로 표현하지 않으며, 1주차 인터뷰와 7주차 사용성 평가로 확인한다.

출처는 강영애·이진영, 시흥시정연구원, 『시흥 거북섬 투어패스 도입을 위한 검토 과제』, SHRI Issue Paper 제15호, 2026.06.30이다. [시흥시정연구원 발간 목록](https://www.shri.re.kr/research/policy/list)에서도 발간 사실을 확인했다. 위 수치는 보고서에 제시된 당시 현황이다.

보고서는 시흥시 전체의 현황 조사가 아니므로 거북섬의 공실률·시설 구성을 시흥시 전역에 적용하지 않는다. 보고서 p.29·표 23은 배곧·시흥시 전역으로의 단계적 확대를 검토안으로 제시한다. 이번 프로젝트는 사용자 요청에 따라 서비스 대상 지역을 시흥시 전체로 정하며, 지역별 수요·시설·이동 여건은 추가 조사한다.

본 프로젝트는 이 지역 현안 가운데 **혜택 조건 안내와 이용 과정의 연결**에 집중한다. 실제 상권 효과는 매력적인 제휴시설 확보, 상인의 참여 조건, 할인 비용 부담에 따라 달라지므로 서비스 시연 결과와 구분해 평가한다.

## 3. 기존 해결방법과 차별성

경기투어패스는 여러 관광시설을 모바일 이용권으로 연결하는 선행 사례다. 경기관광공사의 2026년 4월 27일 발표에 따르면 당시 24·48시간권을 운영하고 관광지·체험시설·카페 등 약 130곳이 참여했다. 이는 통합 이용권 방식이 이미 존재함을 보여준다. [경기관광공사 발표](https://ggtour.or.kr/gto/notice/news/65341210-f7f6-4012-851f-0d93adf9da5e?type=NOTI_REPORT)


| 기존 방법                            | 장점                                      | 이번 프로젝트에서 보완할 지점                                                              |
| -------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 관광 안내 페이지·개별 시설 홈페이지 | 시설 소개와 상세 정보를 확인하는 출발점   | 개별 안내를 확인한 이후의 패스 발급·잔여 혜택·사용 결과를 하나의 흐름으로 연결한다.      |
| 시설별 할인권·쿠폰                  | 특정 시설의 혜택을 직접 제공              | 여러 혜택의 비용·예약·횟수 조건을 같은 형식으로 제시하고, 한 패스에서 잔여량을 확인한다. |
| 경기투어패스                         | 넓은 지역의 시설을 모바일 이용권으로 연결 | 시흥시 가족 방문 상황에 맞춰 지역별 위치와 혜택 조건을 안내하고 현장 사용 절차를 검증한다. |

**차별화 방향은 추천 이유·이용 조건·피드백의 연결**이다. 장소와 테마의 관계를 따라 추천 근거를 제시하고, 본인의 이용 후 평가를 다음 추천 순위에 반영한다. 무료와 할인을 구분하고 본인 부담액, 예약 여부, 유효기간, 남은 횟수를 같은 위치에 표시한다. 담당자는 자신의 가맹점 혜택만 확인하고, 사용 처리 후 방문객에게 동일한 결과가 보이도록 한다.

통합 패스나 중복 사용 방지를 새로운 기술로 주장하지 않는다. 또한 기존 서비스에 조건 안내나 사용 이력이 없다고 단정하지 않는다. 실제 사업으로 발전한다면 독립 서비스를 새로 운영하는 비용과 경기투어패스에 시흥시 상품을 구성하는 방안을 함께 비교해야 한다.

## 4. 핵심 기능과 구현 범위

### 반드시 구현할 기능

아래 우선순위는 개발 순서이며, 모두 필수 완료 범위다.


| 순위 | 기능                     | 제공 내용과 완료 기준                                                                                       |
| ------ | -------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 1    | 혜택 탐색·조건 비교     | 비로그인으로 목록·상세를 보고 혜택 유형, 비용, 예약 여부, 횟수, 기간을 확인한다.                           |
| 2    | 역할별 로그인·패스 발급 | 방문객·담당자·관리자를 구분한다. 방문객 본인에게 유효 패스를 동시에 1개만 발급한다.                       |
| 3    | 내 패스                  | 제시용 코드, 시작·만료 시각, 남은 혜택, 사용 이력을 본인만 조회한다.                                       |
| 4    | 가맹점 사용 처리         | 담당자가 코드를 입력하고 배정된 혜택을 선택·확인한다. 만료·취소·중복·타 가맹점 사용을 거부한다.         |
| 5    | 관리자 관리              | 상품·가맹점·혜택 등록·수정·비활성화와 미만료 패스 취소를 제공한다. 취소 사유와 과거 이력을 보존한다.    |
| 6    | 일관성·보안·재현성     | 동시 요청에도 혜택당 1회만 성공하고, 상품 수정 후에도 발급 당시 조건을 보존한다. 재시작 후 기록이 유지된다. |

시연용 패스는 **발급 순간부터 24시간** 유효하며, 혜택마다 1회 이용한다. 가맹점 A는 가상 체험 1회 무료, 가맹점 B는 가상 음료 5,000원에서 1,000원 할인으로 본인 부담 4,000원이다. 두 혜택 모두 예약이 필요 없고 이용 간격 제한이 없다. 금액은 조건 이해를 위한 허구 예시이며 실제 결제는 발생하지 않는다. 지역 범위·시연 가맹점 배치·세부 판정 규칙은 [제품 범위](spec.md#제품-범위)를 따른다. 목록·상세에는 지역명과 가상 위치 설명을 함께 표시하며, 실제 이동 시간이나 하루에 모든 혜택을 이용할 수 있다고 보장하지 않는다.

### 관광 추천·피드백·온톨로지 — 필수 추가 범위

- **관광 추천:** 지역·관심 테마·동반 유형을 입력하면 장소와 추천 이유를 보여준다. 일반 관광 소개와 패스 혜택 포함 여부를 구분한다.
- **이용 후 피드백:** 본인의 성공한 혜택 사용 이력에서 만족도·사유·의견을 작성·수정·삭제하고 다음 추천에 반영한다.
- **온톨로지 관리:** 관리자가 장소·개념·관계를 관리하고 테마 상위 개념을 통한 추천을 지원한다. 예를 들어 ‘해양 체험’ 장소는 ‘체험’ 관심사에도 연결된다.

권한·입력·예외 조건은 [기능 요구사항 10~13](spec.md#기능-요구사항), 모델·점수·초기 자료는 [추천 설계](tourism-semantics.md)를 따른다. 추천을 비교할 일반 관광 시연 장소를 추가하되 패스는 기존 1종·혜택 2개를 유지한다.

### 여유가 있을 때 구현할 기능

필수 기능과 예외 검증이 끝난 경우에만 혜택 유형 필터, 사용 내역 기간 검색, 관리자용 집계 화면을 추가한다. 집계는 시연 데이터임을 표시한다. 외부 관광정보 자동 연동은 별도 범위 검토 후 결정한다.

실제 결제·환불·정산, 예약·교통·문자 연동, QR, 상용 운영은 이번 구현에서 제외한다. AWS 배포는 공식 과제 요구가 확인된 뒤 결정하며 로컬 Tomcat·MySQL 시연은 필수다.

## 5. 사용자 흐름과 서비스 설계

### 사용자 흐름과 화면 초안

방문객 흐름: **관심 조건 입력 → 추천·이유 확인 → 목록·상세 → 로그인 → 시연 패스 발급 → 내 패스 제시 → 담당자 사용 확인 → 잔여 혜택·사용 내역 확인 → 피드백 → 다음 추천**.


| 장면            | 화면과 사용자 행동                                              | 서비스의 응답                                                                                      |
| ----------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 0. 관광 추천    | 지역·관심 테마·동반 유형을 선택한다.                          | 추천 장소·이유·패스 포함 여부를 표시하고 결과가 없으면 조건 변경을 안내한다.                     |
| 1. 방문 준비    | 보호자가 상세 화면에서 체험·음료 혜택을 비교한다.              | 가맹점의 지역명·가상 위치, 무료/할인, 본인 부담액, 예약 여부, 횟수와 24시간 계산 기준을 표시한다. |
| 2. 발급         | 보호자가 로그인 후 ‘시연 패스 발급’을 누른다.                 | 고유 코드와 정확한 시작·만료 시각을 표시한다. 기존 유효 패스가 있으면 해당 패스를 안내한다.       |
| 3. 제시         | 가맹점 A 방문 상황에서 내 패스의 코드를 제시한다.               | 사용 가능한 혜택과 잔여 횟수를 보여준다.                                                           |
| 4. 사용 확인    | A 담당자가 로그인해 코드를 입력하고 자기 혜택을 선택·확인한다. | 서버가 권한·기간·상태·횟수를 검사하고 성공 시 사용 이력을 저장한다.                             |
| 5. 다음 활동    | 보호자가 내 패스를 다시 확인한다.                               | A는 사용 완료, B는 1회 남음으로 표시한다. B에서도 같은 절차로 이용한다.                            |
| 6. 결과 확인    | 보호자가 사용 내역을 연다.                                      | 사용 시각·가맹점·결과를 보여준다. 담당자는 자기 가맹점 기록만 조회한다.                          |
| 7. 이용 후 평가 | 본인의 성공 사용 이력에서 만족도·사유·의견을 남긴다.          | 피드백을 저장하고 다음 추천에 반영한다. 수정·삭제도 제공한다.                                     |

오류도 같은 흐름 안에서 처리한다. 없는 코드에는 재입력을 안내하고, 만료·취소·사용 완료에는 해당 거부 이유를 표시한다. 실패한 요청은 횟수를 차감하지 않는다. 담당자 화면에 방문객의 다른 가맹점 이용 이력을 노출하지 않는다.

관리자는 별도 화면에서 상품·혜택과 관광 장소·온톨로지 관계를 관리한다. 상품을 바꾸더라도 기존 패스의 발급 당시 조건은 유지되며, 관리자 취소나 가맹점 비활성화는 이후 사용을 차단한다.

화면은 휴대전화에서도 읽을 수 있는 반응형 구성으로 설계한다. ‘무료’, ‘할인’, ‘본인 부담’을 명확히 구분하고 상태는 색상과 글자를 함께 사용한다. 가족 방문은 이용 맥락이며 가족 인원별 통합 발권 기능은 포함하지 않는다.

## 6. 핵심 기술과 구현 가능성

### 기술 구성

강의 스택을 사용해 화면부터 DB 저장까지 직접 연결한다. Java 17, Servlet 6.0, JSP·EL/JSTL 3.0, HTML/CSS/JavaScript로 화면과 요청 처리를 만들고, Tomcat 10.1에서 실행한다. MySQL 8.0과 JDBC로 데이터를 저장한다. Servlet–Service–DAO/DTO 구조를 적용하며 개발 환경과 금지 기술은 [기술 계획](plan.md#기술-스택)을 따른다.

데이터는 사용자·담당자 배정, 상품, 가맹점, 혜택, 발급 패스, 발급 당시 조건, 사용 이력으로 나눈다. 가맹점의 지역명·위치 설명도 저장하고 발급 조건에 포함한다. 상품의 현재 설명과 발급된 패스의 계약 조건을 분리해 수정이 과거 기록을 바꾸지 않도록 한다.

TourAPI의 국문 관광정보 서비스는 REST 방식, JSON/XML을 제공하며 무료다. 공개 안내상 개발 단계는 자동승인, 운영 단계는 심의승인이고 개발계정 신청 가능 트래픽은 1,000으로 표기되어 있다. 실제 적용 전 인증키 발급과 할당량 단위를 확인한다. 사진에는 공공누리 1·3유형이 포함되므로 개별 출처·변경 제한을 확인하고 CI·BI 용도로 사용하지 않는다. [공공데이터포털 이용 조건](https://www.data.go.kr/data/15101578/openapi.do?recommendDataYn=Y)

따라서 API 승인이나 통신 상태와 관계없이 자체 시연 데이터로 핵심 흐름을 완성할 수 있다. 실제 관광정보가 존재한다는 사실을 패스 제휴가 성립했다는 근거로 사용하지 않는다.

### 팀원별 개발 책임


| 팀원     | 담당 기능                                                  | 학습할 기술                         | 예상 기여도 |
| ---------- | ------------------------------------------------------------ | ------------------------------------- | ------------- |
| A [이름] | 목록·상세·공통 화면, 추천 화면·모바일 표시, 사용성 개선 | JSP/JSTL, HTML/CSS, 접근성·폼 처리 | 25%         |
| B [이름] | 패스 발급·내 패스·발급 조건 보존·추천 계산              | Servlet/Service, JDBC, 트랜잭션     | 25%         |
| C [이름] | 담당자 사용 처리·중복 방지·사용 이력·피드백             | MySQL 잠금·제약, 동시성·권한 검증 | 25%         |
| D [이름] | 로그인·권한 Filter·관리자 기능·온톨로지·초기화         | 세션 인증, 암호 해시, 관리자 CRUD   | 25%         |

모든 팀원은 담당 기능의 화면·서버·DB 연결 및 검증에 참여한다. 예상 기여도는 계획값이며 코드 줄 수로 평가하지 않고 완료 기능, 리뷰, 검증, 통합 지원 기록으로 조정한다. C·D의 동시성·보안 업무가 커지면 A·B가 화면과 테스트 작업을 지원한다.

협업은 기능별 작업 이슈와 브랜치, 변경 제안 검토로 진행한다. 주 2회 진행 상황을 공유하고 주 1회 통합 시연한다. 검토자는 A↔B, C↔D로 시작하되 주마다 교체한다. 요구사항은 명세 한 곳에서 관리하고 제안서·README에서는 링크한다.

의견 충돌 시 목표 사용자와 필수 범위, 완료 기준으로 대안을 비교한다. 판단이 어려우면 하루 이내의 작은 시연으로 구현 비용과 사용성을 확인한 뒤 합의한다. 합의되지 않으면 팀 다수결로 결정하고 근거를 기록하며, 과제 해석 문제는 담당 교수에게 확인한다. 일정이 지연되면 선택 기능부터 줄이고 권한·중복 방지·조건 보존은 유지한다.

방문객 3명 이상과 담당자 2명 이상에게 같은 조건의 개별 안내와 패스 화면을 순서를 바꿔 제시한다. 선택·조건 이해·제시·사용·결과 확인의 성공 여부와 시간을 기록하고, 무료·할인 혼동 등 중대한 오해는 수정 후 다시 확인한다. 추천 이유 이해·패스 포함 여부 구별·피드백 작성 성공과 추천 변화 이해도 확인한다. 소규모 평가이므로 지역 전체의 효과로 일반화하지 않는다.

개발 완료의 필수 조건은 **추천·피드백 반영과 설명의 일치, 온톨로지 관계 검증, 핵심 흐름의 연결, 중복 차감 방지, 권한 통제, 재시작 후 기록 유지, 타 팀원의 실행 재현**이다. 공실률 감소나 매출 증가 목표치를 근거 없이 약속하지 않는다.

### 운영 주체와 유지 방법

수업 기간에는 팀이 로컬 시연 환경을 운영한다. D가 계정·권한·초기화, B·C가 데이터 무결성과 장애 확인, A가 안내 문구·사용성 관리를 맡되 변경 사항은 상호 검토한다. DB는 시연 전과 구조 변경 전에 백업하고 복원 절차를 확인한다. 실제 지역 소개는 발표 전 출처와 변경 여부를 다시 확인하며, 시연 기록과 구분해 관리한다.

향후 지역사회 실증에서는 시흥시 관광·상권 관련 부서, 지역 상인 조직, 전문 운영사를 협의 대상으로 제안할 수 있다. 이 기관들의 참여나 운영 책임은 확정되지 않았다. 실제 운영 전 가맹점 모집, 할인 비용 부담, 고객 문의, 결제·취소·정산 책임, 서버·정보 갱신 비용을 정해야 한다. 수수료나 운영 위탁비는 이 조건을 확인한 뒤 검토할 재원 후보다.

실증 시에는 운영자가 영업·혜택 조건의 갱신 담당자와 주기를 정하고, 변경 승인·문의 대응·장애 복구 절차를 마련한다. 개인정보는 필요한 항목만 수집하고 보관·삭제 기준을 확정한다. 수업 평가는 익명 참여자 번호로 기록하며 테스트 계정만 사용한다. 평가 종료 시 불필요한 참여자 기록을 정리한다.

활용은 **수업용 시연 검증 → 실제 방문객·상인 수요 확인 → 참여 의사가 확인된 소규모 제휴 실증 검토** 순으로 진행한다. 첨부 보고서의 중장기 정책 추진안은 참고자료이며 본 프로젝트의 개발 일정이나 확정 사업으로 취급하지 않는다.

발표 시간이 미정이므로 5분을 가정한다. 실제 배정 시간에 비례해 조정한다.

| ------------ | ------------------------------------------------------------------------- |
| 0:00–0:45 | 목표 사용자와 이용 조건 확인 문제, 거북섬 공실 통계의 시점·출처        |
| 0:45–1:20 | 기존 투어패스와 비교, 시흥시 방문 상황에 맞춘 차별화 방향               |
| 1:20–3:00 | 추천 이유 → 발급 → 담당자 사용 → 피드백·다음 추천, 재사용 거부 시연 |
| 3:00–4:00 | 구현 범위·데이터·핵심 기술, 일정과 팀원별 개발 책임                   |
